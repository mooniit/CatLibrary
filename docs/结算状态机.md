# M4 结算状态机

日期均为北京时间。某日的喂食记录用于该日费用判断；次日零点处理刚结束日期的账目。每个家庭日期只有一条执行记录，事务内按家庭、个人钱包的固定顺序加锁。

| 顺序 | 状态变化 | 已确认边界 |
|---|---|---|
| 1 | 已满足条件且已到云端的奖励入账 | 离线/待照片确认的奖励不预支；迟到奖励在实际同步时入当前余额，旧结算不回滚 |
| 2 | 旧欠款计息 | 奖励先抵债；剩余负余额的10%向下取整；新产生欠款当天不计息 |
| 3 | 登记主人支付当天未喂、未出游猫的费用 | 每猫20；逐笔最低余额-150；未付余量取消，不变成隐形欠款 |
| 4 | 双人家庭代扣 | 主人当日新封顶不代扣；已在先前日期封顶且本次奖励后仍欠满时，另一人先处理自己的利息和猫费，再代当日每猫最多20，可欠至-150 |
| 5 | 修缮判定与停费 | 双人先入账本节点合格奖励，再判断双方是否仍为-150；任一人已抵债则当次不触发。单人达到-150后进入修缮；免缴期内不重复触发 |

示例：一人余额0、一只猫未喂且未旅行：首次结算 -20；次日先扣2利息再扣20猫费，成为 -42。若某一步余额 -140、应付20，只扣10到 -150，取消余下10，当次不向另一成员转扣。A 第一天新封顶、B 第二天因代扣新封顶，双人修缮最早在第三天结算开始时触发。

同一主人多猫按领养时间、猫咪 ID 顺序扣费。修缮中一条计时即使在中途达标，剩余时长仍不发币；下一条新计时才恢复奖励。

`settle_family_day` 只供数据库内部调用。本地 Supabase 每小时第1分钟定时补跑，北京时间 00:01 首次处理前一天；恢复后从规则启用日与家庭创建日中较晚者开始，按日期补未结算日，同一家庭日期重复执行不会重复扣款。一个家庭的异常会记录在 `family_settlement_failures`，不阻断其他家庭；修复数据后从该日继续补跑。原版 cron 曾因既存家庭成员缺钱包失败；修正版永久作业已于 2026-09-27 11:01 UTC 实际执行成功，失败表为 0。远端 Supabase 项目尚无，远端定时与暂停恢复仍未实测。
