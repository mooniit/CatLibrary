# 喂食前提醒：21:00 汇总

用户于 2026-10-10 确认：北京时间 21:00，应用内提示，可选择开启系统通知；通知权限拒绝时保留应用内提醒。此决定替代 Q12 中提醒时段和渠道的待定项。当前批次完成服务端规则，客户端展示、通知设置和后台调度继续实施，不将接口部署等同于提醒已经可用。

## 规则与接口

- 登记主人每日一条汇总，仅包含本人猫咪。同一天另一成员已经代喂的猫立即排除。
- 提醒使用云端 UTC+8 日期与时间；21:00 前不生成。21:00 后重新进入可以读取当天的汇总，跨零点不再展示前一天。
- 当天有旅行区间的猫不参与喂食费用提醒，即使已经返程；修缮期及完成后的免缴期也不提醒。这沿用既有费用豁免规则，不改币值、扣费、结算顺序或历史账目。
- 一旦生成，同一天只移除已喂食、旅行等不再符合条件的猫，不因为新领养或重试追加第二条汇总。主键是本人身份与北京时间日期。
- `get_feeding_reminder()` 无参数；本人、家庭、时间、猫咪名单和收费豁免由服务端判断。返回 `before_time`、`empty` 或 `ready`；只有 `ready` 包含本人、家庭、日期、当前名单及两条渠道的已展示标记。
- `ack_feeding_reminder(target_day,target_channel)` 仅支持 `in_app` 和 `notification`，只确认本人已有记录。重复确认保留第一次时间；没有记录返回 `not_found`。不改另一成员记录，不创建提醒，不触发喂食或扣款。
- 表仅开放本人读取，没有客户端写入权限。测试用带时钟的内部函数不向 authenticated/anon 开放；正式调用不能注入时间。

## 客户端接入待完成

首页以简短猫爪提示展示当天名单，点击进入猫咪管理；保持现有白色/雾蓝夜晚主题，避免新增长篇卡片。已喂食或旅行后重新核对并撤销不再符合条件的提示。记录展示确认，丢失确认回执时重试同一日期/渠道，不重新生成提醒。离线不能凭本机钟或旧猫咪列表推断正式提醒。

系统通知必须有独立开关及权限说明，默认由用户选择开启。采用相同云端汇总，拒绝通知权限不能关闭应用内提醒。关闭应用时的 21:00 调度、后台身份安全恢复、断网补查、Android 通知取消与 iOS 支持仍未实现；不能用前台显示一次通知或旧缓存定时弹出代替这些条件。后续分别做原生和真机验收，不请求其它成员代为开启通知。

## 本批验证

`supabase/tests/feeding_reminders.test.sql` 定向 28 项通过：21:00 边界、日期、本人范围、重复请求/丢回执重查、成员代喂、双渠道独立确认、越权、伪造时间/写入拒绝、全喂后撤销、跨日、当日已返程、修缮与免缴、钱包账本不变。新 fixture 全部在事务中回滚，没有清理已有数据。

完整本地数据库 34 文件、461 项通过。首次全库运行发现旧修缮测试读取全表而误用保留的其它测试家庭；已限定自身家庭/修缮事件。失败记录保留本机，正式通过记录见 `docs/evidence/m7-feeding-reminders-db.txt`。

仅一条新迁移经 dry run 后部署至既有免费项目，无 seed/Vault/reset，没有新增收费作业。远程使用一位新的匿名身份，只检查 API 与权限，不初始化钱包、不建家庭、不领养：7 项通过，见 `docs/evidence/m7-feeding-reminders-cloud.json`。此验证不包含实际 21:00 原生通知、关闭应用的后台运行、原手机账号或 iPhone。

本地已应用的任务计时与本批提醒迁移补登迁移历史，避免以后正常迁移重复建表；只登记已存在且通过回归的两条版本，不重新执行业务函数。普通 0.1.20+21 APK 与应用源码未变，手机没有安装新包。
