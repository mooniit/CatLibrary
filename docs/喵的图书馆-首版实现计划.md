## 1. 目标与执行原则

依据[首版需求文档](D:/2DoProjects/CatLibrary/docs/喵的图书馆-首版需求文档.md)，交付可在 Android 与 iPhone 上共同使用的首版：个人学习获得资源，两人共同养猫、布置书房、旅行收集，并执行确定的收支与修缮规则。

需求确认不代表文末 Q01～Q12 已经有答案。这些事项仍在相应阶段结合原型或测试结果确定；本计划不替用户决定猫咪性格、商品价格或新的货币规则。

执行方式：

- 先做可看的界面原型与关键技术验证，再按完整用户流程逐步实现。
- 每个阶段产生能演示、能验证的成果；不先堆完全部数据库，再最后连接页面。
- Flutter + Flame + Supabase + SQLite/Drift 保持不变；具体依赖版本在环境验证后锁定。
- 暂定采用功能目录、少量共享基础组件，不建设通用插件平台、微服务或另一套管理后台。
- 货币只由云端正式入账，客户端负责展示和保存待同步记录。
- 货币变更同时维护[货币规则](C:/Users/26424/Desktop/创作计划/ToDo/theLiberary/货币规则.md)及需求摘要。本次计划没有修改货币数值。
- 阶段检查通过后推进；界面和待定规则需要决策时，提供具体画面或案例再讨论。
- 已暂停的旧演示不恢复为独立项目。可用部分经检查后纳入正式工程。

### 4.2 云端与本机职责

| 对象 | 云端正式记录 | 本机用途 |
|---|---|---|
| 用户、家庭与邀请 | 身份、成员、容量和审批状态 | 会话及已取得资料缓存 |
| 钱包、奖励与支出 | 整数余额、收支流水、请求处理结果 | 余额缓存、待结算展示 |
| 学习 | 已提交分段、确认状态、每日汇总 | 正在计时、可靠检查点、待传照片及记录 |
| 猫咪与喂食 | 主人、外观、名称、每日喂食记录 | 展示与动画 |
| 家具与布局 | 所有权来源、库存实例、布局版本、编辑权 | 当前布局及未保存草稿 |
| 旅行与收藏 | 出发/返回时间、目的地、每猫访问记录、收藏实例 | 倒计时和已获取资源缓存 |
| 修缮 | 家庭状态、窗口起止、有效进度、免缴日期 | 展示、尚未同步的计时记录 |

关键约束：

- 每条学习记录、消费及布局保存使用稳定的请求编号；超时重试返回同一处理结果。
- 余额变化与对应业务记录在同一数据库事务内完成。例如买家具不能只扣钱而漏发物件。
- 以家庭为单位协调跨成员结算，保持固定加锁顺序，避免代扣时彼此等待或重复扣款。
- 不把整套客户端状态直接覆盖到云端；上传明确的操作或学习记录，由服务端检查。
- 布局实时消息只提示版本变化；钱款与猫咪状态重新读取正式状态。重连也执行核对。
- 用户以 Supabase 独立匿名身份进入，身份来自会话，不接受客户端自行指定付款人。匿名用户也是经过认证的用户，与公开 API key 不同。[Supabase 匿名身份说明](https://supabase.com/docs/guides/auth/auth-anonymous)
- 家庭数据通过数据库行级权限限制访问；私有照片同样按家庭关系授权。权限规则不是只在界面隐藏按钮。[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

### 4.3 时间处理与必须先验证的问题

- 持久化保存明确时间戳，按 UTC+8 推导业务日期；可注入测试时钟，避免靠改手机日期测试。
- 正常后台经过时长与进程意外终止需要区分。系统不保证发送最后一条生命周期通知，不能靠退出回调精准保存结束时刻。[Flutter 生命周期说明](https://api.flutter.dev/flutter/dart-ui/AppLifecycleState.html)
- **后台跨零点是一项早期验证重点**：手机可能暂停代码运行，服务端又不能单凭“用户曾点击开始”无限推算有效学习。T03 必须明确在线分段、后台保存、云端可结算证据及延迟同步的边界。
- 不将无法证实的后台时长提前发奖，也不擅自把已确认的跨零点自动入账改为一律下次打开才到账。若两项体验无法同时保证，拿设备实测案例确认调整，并同步需求与货币文件。
- 旅行、72 小时修缮和费用日期由服务端状态判断；手机倒计时只负责显示。
- 定时任务可以延迟或重试，业务结果仍应唯一。免费项目暂停后的补处理是否重放日期，按 Q10 确认，不能擅自免除或追补费用。

## 5. 验证方式与任务尺寸

### 5.1 命令约定

下列为后续环境就绪后的目标命令，均未在本次规划中执行。

| 标识 | 验证内容 | 命令或方法 |
|---|---|---|
| ENV | 开发环境 | flutter doctor -v；flutter devices |
| STATIC | 格式和静态检查 | dart format --output=none --set-exit-if-changed lib test；flutter analyze |
| UNIT | 客户端规则/组件测试 | flutter test |
| DB | 本地数据库规则/权限测试 | supabase start；supabase test db |
| ANDROID | 安卓构建与真机 | flutter build apk --debug；在已选 Android 设备运行 flutter run |
| DEVICE | 移动端完整流程 | 连接目标真机后执行 flutter test integration_test；补充无法自动化的锁屏/系统终止操作 |
| IOS | iOS 构建与真机 | 在 Mac 上执行 flutter build ios --debug --no-codesign；完成开发签名后使用 flutter run 真机验证 |
| MANUAL | 指定人工场景 | 记录设备、应用版本、步骤、预期、实际结果及截图/日志 |

DB 只针对本地可重建测试环境；不在正式数据上运行重置操作。数据库测试依赖本地 Supabase/Docker 就绪，T01 记录实际启动情况。

iOS 无签名构建只能证明编译，不能证明手机可安装。需在 M0 明确 Mac、签名和 iPhone 测试途径。Flutter 官方将 iOS 开发环境限定为 macOS。[平台环境说明](https://docs.flutter.dev/platform-integration)

### 5.2 完成标准

- 每个任务先完成所列针对性验证；阶段结束再运行受影响模块回归及构建。
- 每两到三个任务设一次检查，业务逻辑完成即与页面连接，保持可演示。
- 每次实际执行包以 1～5 个手写文件为目标；生成的平台文件、锁文件、图片批次单独记录。
- 若一个编号需要更多文件或无法在一个集中工作段验证，先按“服务端规则 → 客户端接入 → 异常验证”拆成子任务，再执行；不得把大编号直接当一次整包提交。
- 文件范围是定位线索，不是要求预先一次建完所有文件。
- 检查项默认未完成，不以“代码写了”代替“验证通过”。

## 9. 主要风险与处理

| 风险 | 影响 | 提前处理 |
|---|---|---|
| 后台暂停与意外终止难以精确区分 | 有效时长、跨日自动入账可能与预期不符 | T03 双平台实测并固定可解释方案，T10 复验 |
| 免费云端连接或暂停 | 同步、定时结算可用性 | T04 验证实际网络和恢复策略，T18 测试可重试结算 |
| 同一零点多种状态变化 | 利息、代扣、修缮判定错误 | T18 前确定事件次序，统一家庭结算事务与案例 |
| 多人并发和丢回执 | 重复扣费、发奖、覆盖布局 | 请求唯一编号、原子事务、版本校验、故障注入 |
| 详细猫咪和大量高清素材 | 动画成本与手机纹理内存 | T02 确认风格，T23/T24 先测少量素材，T33 分批验收 |
| iOS 环境晚到位 | 无法满足首版双平台 | M0 明确环境和签名途径，核心阶段保留 iPhone 实测 |
| 匿名会话丢失 | 原身份无法恢复 | 不新增恢复产品范围；避免正常启动重复建身份，记录当前限制 |
| 待定内容被临时值替代 | 实际产品偏离确认需求 | 测试配置与正式配置分开，阶段出口检查待定项 |

不承诺未经验证的总工期。完成 M0 后，根据环境、素材供给和真实计时验证结果再估算；每完成一个阶段更新剩余工作。首个完整业务演示目标是 M2 的“学习 → 入账”，日常养猫闭环在 M4 完成，完整首版需到 M8。
